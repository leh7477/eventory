## 0. 현재 구조

```
손님 브라우저
   │
   ├─ 공개 페이지   서버컴포넌트 ─ anon키 ─→ Supabase (읽기 전용, RLS 공개)
   ├─ 견적 문의     브라우저 ────── anon키 ─→ Supabase (INSERT만 허용)
   │
관리자 브라우저
   └─ 관리자 화면   서버액션 ─ service_role키 ─→ Supabase (RLS 우회)
                     ↑
              여기서만 민감 데이터를 다룬다
```

| 구성요소 | 역할 |
|---|---|
| Next.js (OCI 134.185.108.37:3001) | 화면 + 서버 로직 |
| PostgreSQL (Supabase) | 데이터 저장 |
| PostgREST (Supabase) | 테이블을 자동 REST API로 노출 |
| GoTrue (Supabase Auth) | 관리자 로그인 |
| RLS (Postgres) | **실질적 유일한 방어선** |

핵심: PostgREST 때문에 브라우저가 DB에 직접 닿을 수 있다.
그래서 보안은 애플리케이션 코드가 아니라 **RLS 정책**이 결정한다.

## 1. 환경 분리 — 가장 먼저 고칠 것

### 지금 문제
개발용 `.env.local`과 운영 서버가 **같은 Supabase 프로젝트**를 본다.
로컬에서 테스트하면 **실제 고객 데이터가 들어있는 DB가 바뀐다.**

### 기준
| 환경 | 용도 | DB |
|---|---|---|
| 개발 (내 PC) | 기능 만들고 시험 | **별도 Supabase 프로젝트** |
| 운영 (OCI) | 실제 서비스 | 현재 프로젝트 |

### 방법
1. Supabase에서 프로젝트를 하나 더 만든다 (무료 플랜 2개까지)
2. `supabase/schema.sql` 전체를 새 프로젝트 SQL Editor에 실행
3. 내 PC `.env.local`을 새 프로젝트 키로 교체
4. 운영 서버 `.env.local`은 건드리지 않는다

### 규칙
- 운영 DB에 테스트 데이터를 넣지 않는다
- 불가피하게 운영에서 확인해야 하면 `ZZ` 접두사를 붙이고 **즉시 삭제 + 건수 대조**
- 운영 `service_role` 키는 서버 `.env.local`에만 둔다. 채팅·메신저로 보내지 않는다

## 2. 스키마 변경 워크플로우

### 지금 문제
`schema.sql` 한 파일에 `alter table ... add column`이 56개 쌓였다.
버전 표기가 없어 **파일과 실제 DB가 같은지 확인할 방법이 없다.**
(지금도 그렇다: `schema.sql` 에는 `audit_log` 테이블과 `privacy_agreed_at`
컬럼이 적혀 있지만 실제 DB에는 아직 없다. 파일은 "이래야 한다"는 선언일 뿐,
실제와 같은지는 **아무도 보증하지 않는다**.)

### 기준: 변경은 파일에 먼저, DB에 나중

```
1) supabase/migrations/YYYYMMDD-설명.sql 로 변경분만 새 파일 작성
2) 개발 DB에 실행 → 화면에서 확인
3) git commit
4) 운영 DB SQL Editor에 같은 파일 실행
5) 배포
```

### 작성 규칙
- 항상 `if not exists` / `drop policy if exists` — 여러 번 실행해도 안전하게
- 컬럼을 **지우지 말고** 안 쓰는 상태로 둔다. 지우려면 한 달 이상 관찰 후
- 한 파일에 한 가지 목적만

### 정리 대상 (확인된 것)
| 항목 | 문제 |
|---|---|
| `schedules.vendor` (text) | 거래처와 이름으로 연결 → 이미 고아 데이터 발생 |
| `inquiries` 정산 컬럼 10개 | 성격이 달라 별도 테이블이 맞음 |
| `inquiries.name`, `event_date` | 구버전. 사용 0건 |

## 3. 백업과 복구

### 지금 문제
**백업이 하나도 없다.** 날아가면 복구 불가.

### 기준
| 무엇 | 주기 | 보관 |
|---|---|---|
| DB 전체 덤프 | 매일 새벽 | 30일 |
| 배포 직전 수동 덤프 | 배포 때마다 | 7일 |

### 준비
1. Supabase 대시보드 → Settings → Database에서 **연결 문자열** 확보
   (service_role 키로는 백업 불가. DB 비밀번호가 따로 필요)
2. 서버에 `postgresql-client` 설치 (`pg_dump` 사용)
3. cron 등록 — 기존 stock-app cron과 같은 서버라 형식을 맞춘다

### 복구 훈련
**백업은 복구해봐야 백업이다.** 분기 1회, 개발 DB에 덤프를 복원해
정상 동작하는지 확인한다. 안 해본 백업은 없는 것과 같다.

## 4. 배포 절차

### 방법
```bash
npm run deploy
```

`git pull` 만 하면 서버의 `package-lock.json` 이 npm 때문에 바뀌어 있어
`--ff-only` 가 막히고, **빌드했다고 착각한 채 옛 코드가 그대로 도는** 일이 있었다.
`npm run deploy` 는 서버 로컬 변경을 버리고, 받은 버전이 실제로 맞는지 확인하고,
재시작 후 응답할 때까지 기다린 뒤 주요 페이지와 somtip.kr 까지 확인한다.

### 기준
```
1) 로컬 npm run build 통과 확인
2) 개발 DB로 화면 확인
3) commit + push
4) (스키마 변경이 있으면) 운영 DB에 마이그레이션 먼저 실행
5) 서버 pull → build → pm2 restart
```

### 주의
- **스키마 변경은 배포보다 먼저.** 순서가 바뀌면 "컬럼 없음" 오류로 화면이 죽는다
- 손님이 쓰는 시간대(낮)는 피한다. 배포 중 열어둔 탭은
  `Failed to find Server Action` 오류가 난다 (현재 로그에 146건)
- 되돌리기: `git revert` 후 같은 절차. DB 변경은 되돌리기 어려우니 신중히

## 5. 이력·감사 로그

### 법적 의무
개인정보 안전성 확보조치 기준 제8조 —
**개인정보 취급자의 접속기록을 1년 이상 보관**해야 한다.

### 현황
| 계층 | 상태 |
|---|---|
| 앱 로그 (pm2) | 있음. 단 logrotate 없어 무한 증가 |
| 접속 기록 | **없음** (nginx를 거치지 않음) |
| 데이터 변경 이력 | 견적·일정·매출만 (`activity_log`) |
| 로그인 이력 | 우리 쪽 기록 없음 |

### 기준
1. `pm2 install pm2-logrotate` — 로그 무한 증가 차단
2. nginx를 거치게 해서 접속 기록 남기기 (HTTPS 작업과 함께)
3. 이력이 없는 영역에 `activity_log` 방식 확대 — **재고·단가·거래처** 우선
4. 개인정보 조회 기록: 누가 언제 고객 연락처를 열었는지

### 이력 기록 형식 (기존 방식 유지)
```json
{"at":"2026-09-12T13:51:37Z","by":"tnsqhr0629","action":"계약 금액 1,000,000원 입력"}
```
언제 / 누가 / 무엇을 — 이 세 가지는 반드시 남긴다.

## 6. 권한 원칙

### 지금 문제
서버 액션 61개 전부가 `requireAdmin()`(로그인 여부)만 확인하고
**메뉴 권한은 확인하지 않는다.** 미들웨어는 화면 이동만 막는다.

지금은 계정 3개가 모두 최고관리자라 노출이 없지만,
**사무직원을 뽑는 순간 문제가 된다.**

### 기준
| 원칙 | 내용 |
|---|---|
| 최소 권한 | 직원에게는 업무에 필요한 메뉴만 |
| 서버에서 재확인 | 화면에서 가렸다고 안전하지 않다. 액션마다 권한 확인 |
| 계정 공유 금지 | 누가 했는지 추적이 불가능해진다 |
| 퇴사 시 즉시 삭제 | ID 관리에서 당일 처리 |

### 할 일
`requireAdmin()` → `requireSection('rates')` 형태로 액션마다 필요한 메뉴를 지정.
`lib/admin/sections.js`의 `canAccess()`를 그대로 쓰면 된다.

## 7. 보안 기준선

| 항목 | 현재 | 목표 |
|---|---|---|
| HTTPS | ❌ 평문 HTTP | Cloudflare + nginx |
| origin 직접 노출 | ❌ 3001 포트 열림 | Cloudflare IP만 허용 |
| service_role 키 유출 | ✅ 브라우저에 없음 | 유지 |
| 고객 데이터 익명 조회 | ✅ 차단됨 | 유지 |
| 문의 스팸 방지 | ❌ 무제한 등록 가능 | Cloudflare 봇 차단 |
| 관리자 비밀번호 | 최소 6자 | 10자 이상 |

**Cloudflare를 붙일 때 반드시 함께:**
origin(134.185.108.37:3001)이 열려 있으면 Cloudflare를 우회할 수 있다.
방화벽에서 Cloudflare IP 대역만 허용해야 실제로 보호된다.
