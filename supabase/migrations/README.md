# 스키마 변경 관리

## 두 파일의 역할

| 파일 | 역할 | 언제 쓰나 |
|---|---|---|
| `../schema.sql` | 전체 스키마 (처음부터 재생성용) | 새 Supabase 프로젝트를 만들 때 통째로 실행 |
| `migrations/*.sql` | 변경분만 (날짜순) | 기존 DB에 변경을 적용할 때 |

## 규칙

1. 스키마를 바꿀 일이 생기면 `YYYYMMDD-설명.sql` 파일을 새로 만든다
2. 항상 `if not exists` / `drop policy if exists` 를 써서 **여러 번 실행해도 안전하게**
3. 한 파일에 한 가지 목적만 담는다
4. 개발 DB에 먼저 실행 → 화면 확인 → commit → 운영 DB 실행 → 배포
5. **컬럼을 바로 지우지 않는다.** 안 쓰는 상태로 한 달 이상 두고 관찰한 뒤 지운다
6. 적용한 파일은 지우지 않는다 (이력이 곧 문서다)

## 적용 순서

배포보다 **스키마 변경이 먼저**다. 순서가 바뀌면 "컬럼이 없다" 오류로 화면이 죽는다.

```
1) Supabase 대시보드 → SQL Editor
2) 아직 실행하지 않은 파일을 날짜순으로 실행
3) 그 다음 코드 배포
```
